# 请求内容与特征监控

调用监控的账号、API Key 账号明细、实时记录优先展示凭证对应的邮箱；未获取邮箱时回退凭证文件名。脱敏开关同时控制邮箱显示及请求原文弹窗。

“实时”列表展示请求 SHA-256 指纹、消息数、工具数，以及请求详情入口。关闭脱敏后可查看客户端原始请求与网关上游请求的 system、messages、tools、生成参数，每部分附带 SHA-256 和 UTF-8 JSON 字节数。JSON 对象键排序后计算指纹，数组顺序及文本空白保留。

客户端采集支持 OpenAI Chat、Responses、Anthropic Messages、Gemini JSON 请求格式。上游内容取自 Antigravity 的最终请求体，包含转换/补充后的内容；重试只保留最终调用监控记录关联的请求体，不逐次保存重试历史。multipart 图片上传没有客户端 JSON 快照，但上游内容仍可保存。

原文保存在 SQLite `call_records.request_details`，摘要保存在 `request_features`。列表和内存缓冲区仅保留摘要；原文通过面板鉴权的 `GET /call-monitor/content?request_id=…` 按需加载，响应禁止缓存。正文与调用记录共用现有保留期及清理逻辑；历史记录无法补回原文。客户端入口不采集请求头或 URL 中的密钥，正文中的业务数据按原文保存。

数据库启动时自动补列，无需手工迁移。仅已进入现有计费/调用监控记录流程的请求会保存内容；鉴权或参数校验阶段拒绝的请求不产生此类记录。未接入计费监控的其他通道不因此新增调用记录。


“实时”列表主列优先显示上游耗时，鼠标悬停查看：

- 上游耗时：该条记录最后一次上游推理尝试发起至收到最后一段响应数据，包含连接建立；原生传输包含本机 helper 一跳。不会被 OAuth、凭证探测覆盖。
- 下游发送耗时：各次 ASGI 正文 `send` 调用耗时之和，不包含等待上游首段、后续数据或业务处理的时间。表示应用向网络层写出，无法证明远端客户端实际收完，也不包含反向代理缓冲。
- 辅助项：上游首字节等待、客户端响应等待（请求进入应用至开始发送非空正文）、请求总耗时（请求进入应用至最后一次正文发送完成）。总耗时包含等待，不等于下游发送耗时。

流式收发可能重叠，这些数值不能直接相加减；不能用总耗时减上游耗时推算下游发送耗时。SSE 首段可能是协议事件，不等于首个文本 token。断连时不虚构请求完成时间。

主列在新上游耗时未采集时回退原网关处理耗时，并在悬浮中注明。历史数据不推算新指标；未接入的传输、尚未采集的阶段显示“未采集”。仅进入现有调用监控的请求保存这些字段，不额外生成调用记录。

计时独立于正文采集开关。每个在飞请求仅有固定字段的计时对象，不保存正文、逐块时间线或重试历史，不增加后台任务、全局请求映射或无界队列。请求完成后更新现有 SQLite 记录和固定长度内存缓冲；数据随原记录按保留期删除。


慢请求诊断额外保留固定数量的阶段时间点（请求体接收完成、鉴权起止、API 进入、上游发起/最后数据、计费开始、监控写入起止），以及 stream、消息/工具数量、数值生成参数和输出格式类型。它们独立于正文采集开关，不包含正文、工具定义、URL 或密钥；不保留逐块或逐次重试历史，未知阶段名称不进入缓存。数据仍复用固定长度缓冲和原保留期。

### 实时列表的最近 1,000 条

配置 `REDIS_URL` 后，主库提交一批调用记录，后台任务随即把该批的记录 ID、时间、账号、密钥 ID 和成功状态更新到 Redis，只保留入库 ID 最大的 1,000 条。刷新列表时先向主库读取窗口版本和当前 TOS 排除名单，再用缓存计算筛选结果、页码和计数。本页的详情和耗时仍从主库读取。

未配置 Redis 或连接超时时，列表沿用主库最近 1,000 条查询。缓存丢失、漏掉批次或遇到乱序提交时，服务根据主库版本校验窗口，并从主库重建最近 1,000 条。

### 历史范围的增量汇总

PostgreSQL 和 SQLite 在写入调用记录的同一事务内累计北京时间自然日和 5 分钟汇总。账号和密钥概览从汇总计算调用数、成功率、按有效样本加权的平均耗时、Token、金额及最近状态。账号的 TOS 排除规则在读取时生效。

今日和全部概览只读汇总。滚动 7 天和 30 天保留精确到请求时刻的起点，起点所在的不足 5 分钟区间按时间索引读取明细。实时列表先从日和 5 分钟汇总定位所选页，再读取对应时间段的记录。最近入库 1,000 条仍使用原有实时窗口。

首次查询旧库时，面板提示正在构建历史汇总。后台从最近的日期开始，按批提交，重启后从持久化的待处理区间继续。清理过期记录或更正历史记录时，受影响的区间会重新汇总。面板等待所选范围就绪后再展示精确结果。PostgreSQL 回填每批最多 8 个连续的 5 分钟段，重建日汇总时只读相应日期的 5 分钟汇总。每批事务与同一日期的调用记录写入互斥，繁忙日期的首次回填可能增加监控写入等待。

本地可使用独立 PostgreSQL 验证百万行数据，设置 `TEST_MAIN_POSTGRES_DSN` 和 `TEST_MONITOR_SCALE=1` 后运行 `python -m pytest tests/test_main_postgres.py -s -k monitor_history_million`。测试创建临时 schema，比较账号、密钥汇总与直接聚合的结果，并核对深分页的记录 ID。

### 文本取号的冷却缓存

PostgreSQL 主库的 Antigravity 常规文本取号使用 `REDIS_URL` 跨 worker 共享候选账号的时间快照。账号临时冷却与额度恢复时间适用于该账号的所有模型，模型冷却按完整模型名分别判断。对某个账号请求某个模型，所有相关时间都已到期才可领取。固定账号与本次已排除的账号仍参与筛选。

全部候选都在等待时，请求计时里的 `credential_cooldown_cache_hit` 记录直接返回所用的毫秒数。可确定恢复时间的缓存命中会用最早可用候选计算 429 的 `Retry-After`。混合号池仍在主库事务中领取。缓存按需在后台重读，快照至多有效 1 秒，因此手动提前解禁或新增账号最多有 1 秒可见性延迟。未配置 Redis 时使用进程内快照，Redis 故障时可回源 PostgreSQL。图片租约与休眠时段的专用领取路径沿用原有逻辑。

Redis 中每个限制对应一个独立 key。以账号 `a.json` 为例，可用 `redis-cli --scan --pattern 'gcli:cooldown:v2:*:a.json:*'` 找到该账号的标记，再用 `TTL <完整 key>` 查看剩余秒数。`:a.json:model:gemini-A` 只限制模型 A，`:a.json:usage` 和 `:a.json:hold` 对该账号所有模型生效。普通标记值为 `1`，到恢复时间自动消失。账号名和模型名中的分隔符使用百分号编码。候选名单按取号流量刷新，Redis 没有近期名单时先查主库。提前解禁会在下次同步时删除旧标记；长期没有取号时，标记按最后一次同步的截止时间自行过期。

文本请求首次取号时按配置的降级顺序尝试，从请求模型所在的位置开始。每一跳独立检查该模型的 key，并同时检查账号共用的额度和临时冷却 key。找到可用账号就使用对应模型。整条可尝试的链都无号时，429 的 `Retry-After` 取各跳中最早已知的可用时间。Redis 候选名单尚未建立时，PostgreSQL 常规领取路径也会计算该时间。仅允许单一模型的密钥只检查获准模型。

生产日志 `[CLAIM_COUNTS]` 按 worker 输出上一个有流量的 UTC 分钟。常规文本取号成功执行的物理 SQL 数为 `2 × claim_batches + snapshot_reads`（每个批次一次锁查询、一次领取查询）。`cache_hits` 是直接从冷却缓存返回的逻辑领取次数。认证、告警和调用记录查询单独统计。
