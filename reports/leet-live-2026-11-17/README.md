## 实际输出证据

原文 JSON 输出：

```json
{"tool":"read_file","path":"/home/user/project/config.json","mode":"auto"}
```

两个混淆变体均输出：

```json
{"t00l":"r34d_f1l3","p4th":"/h0m3/vs3r/pr0j3ct/c0nf1g.js0n","m0d3":"4vt0"}
```

工具定义未混淆，三组均调用了 `read_file`；但两个混淆变体的参数都是：

```json
{"path":"/h0m3/vs3r/pr0j3ct/c0nf1g.js0n"}
```

## 结论与边界

在这组小样本中，模型能理解混淆后的简单自然语言和否定约束；但精确字符串发生确定性的输入破坏，模型照着改变后的值输出或调用工具。这不应笼统归为模型曲解语义，损坏首先发生在整段字符替换阶段。附加“先理解提示词”的引导没有恢复精确字符串。

所有原文请求也都成功，因此本次没有原文触发 429 的对照证据，不能证明 Leet 减少 429。短时间 HTTP 200 不能证明以后没有 403 或留存审计结果。单账号、单模型、每格一次，不可外推为通用成功率。未使用用户真实对话，未测试长提示词、多轮任务或其他模型。

建议保持默认关闭；不对含工具名、路径、URL、代码、JSON 字段等精确字符串的 system 整段使用。若继续迭代，需先设计可验证的精确字符串保护规则，再单独评估。
